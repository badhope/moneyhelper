# 4.17.0 平台压测报告

> 生成时间：2026-11-24 08:48（Asia/Shanghai）。脚本：`scripts/stress_platform.py`；原始结果：`docs/stress-4.17.0.json`。
> 环境：当前云主机，SQLite 本地文件，临时数据目录，不触碰真实账本。

## 测什么

| 场景 | 口径 | 目的 |
| --- | --- | --- |
| 个人千万级资产 | 2,001 个持仓，总市值 10,200,000 元；五维健康评分跑 100 次 | 验证持仓规模上来后是否出现超时或数值退化 |
| 企业多主体多税种 | 100 个主体 × 12 个月，1,200 次税负测算 | 验证批量计税的吞吐与失败率 |
| 企业总账 | 10 个租户 × 12 个期间 × 20 张凭证，共 2,400 张 | 验证多主体多期间的建账、过账路径 |
| SQLite 并发写 | 32 个并发写者 × 20 笔流水，共 640 笔 | 验证写锁、busy_timeout 与错误率 |

## 结果

| 场景 | 样本 | 结果 |
| --- | --- | --- |
| 个人千万级资产 | 100 次 | P50 0.331ms / P95 0.353ms / 最大 0.398ms；评分 96（A） |
| 企业多主体多税种 | 1,200 次 | 0 失败；P50 0.018ms / P95 0.022ms / 最大 0.051ms；税额合计 488,715,416.91 元 |
| 企业总账 | 2,400 张凭证 | 2.533s；947.3 张/秒 |
| SQLite 并发写 | 640 笔 | 0 错误；4,512.3 笔/秒；P50 4.524ms / P95 13.566ms / 最大 14.242ms |

## 怎么读

- 计算层不是瓶颈：个人 2,000 持仓、企业 1,200 次计税都在亚毫秒到几十微秒级。
- 总账写入接近千张/秒，适合中小企业的月结批量；集团级上万张凭证需要分批与后台任务，不应在 HTTP 请求里同步跑完。
- 32 并发写零错误，但 P95 已到 13.6ms；再往上加写者，SQLite 单写锁会成为瓶颈。生产上多用户高并发应走队列/批处理，而不是无限加连接。
- **这些数字只证明“确定性计算与本地 SQLite 路径”可用，不证明“100% 场景覆盖”，也不覆盖税局、银行、券商等外部接口。**
