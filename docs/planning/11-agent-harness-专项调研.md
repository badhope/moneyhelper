# Agent Harness 专项调研（M0.8）

> **归档说明**：本文档记录 2026-10 当时的规划与调研过程，**不代表当前实现**。
> 当前状态以 [PROGRESS.md](../PROGRESS.md) 与代码为准；文中提到的 mem0、自研规则引擎、
> `react_agent`、OpenTelemetry 等已在 2.3.0 移除，多租户在 2.4.0 引入。

> 调研对象：ZCode（Z.ai 官方 ADE）、DeepSeek Harness（dsh）
> 目的：把"别人怎么把 Agent 跑稳"拆成六个可比维度，得出 Moneyhelper 可落地的清单
> 结论先行：**Moneyhelper 不缺 Agent 能力，缺的是执行环境的确定性**。四份 harness 的共性
> 价值集中在"工具面收窄、上下文可控、副作用可审批"这三件事上。

## 一、六个维度对照

| 维度 | ZCode | dsh（DeepSeek Harness） | Moneyhelper 当前 | 差距判断 |
|---|---|---|---|---|
| 架构 | 分层模型（Flash 基础 + 代码专长微调上层） + 任务工作区分组 | 无内核，全部是 Cordis 插件：模型/工具/技能/会话/沙箱/存储/循环/调度/UI 可替换 | LangGraph 图 + 手写 tool loop 并存；db 已按域拆分 | Moneyhelper 的编排层有两套（agent_graph / agent.py），属于真实技术债 |
| 工具面 | 按任务分组暴露，工具随分组切换 | 插件注册，权限声明在插件元数据里 | 一套全量工具 + 三个 agent 白名单（bookkeeping/portfolio/supervisor） | 白名单是静态的，不随任务阶段变化 |
| 上下文 | Zread 知识库把上下文做成产品功能 | 事件源会话日志，可回放重建 | tiktoken 精确计数 + 会话摘要压缩（`context.py` + `ensure_session_summary`） | 摘要压缩有，但"按需检索历史"没有 |
| 沙箱 | 桌面/浏览器/终端三形态隔离执行 | 沙箱是插件，可换实现（容器/进程/远程） | 无沙箱：工具直接改本地库 | 财务场景反而更需要——写操作必须可审批 |
| 审批 | 人在编辑器里决策（"AI 是开发主角，人只做决策"） | 权限边界写在插件元数据，由宿主裁定 | 大额阈值 HITL + 待确认 token 一次性消费 | 有雏形，但只覆盖记账；卖出/清仓等同样危险的动作没纳入 |
| 可观测 | Git 分组图谱 | 事件流本身就是审计 | provenance（每个金额变动留痕）+ audit_log + metrics | 审计比两者都细，但缺"回放"能力 |

## 二、ZCode 深读

**核心主张**：AI 是开发主角，人只做决策。产品形态是"分组式任务工作区"——
任务按目标分组并行推进，每组有自己的上下文与工具。

**架构可抄点**

1. **分层模型路由**。基础模型做快速推理，专长模型做深度任务。Moneyhelper 的
   `llm.py` 已有 fallback 链（主模型失败切廉价备选），但缺"按任务难度选模型"——
   现在是一刀切。
2. **任务分组 = 部门模式的组织学**。Moneyhelper `department.py` 已经按
   bookkeeping/accounting/risk/invest 四部门并行，与 ZCode 的分组工作区同构。
   差别在 UI：ZCode 把分组可视化，Moneyhelper 只有 JSON 输出（`/api/department/run`）。
3. **Zread 知识库**。把"项目知识"做成可检索资产。Moneyhelper 的对应物是
   `memory.py` + `reflections`，但只在问答时注入，没有独立检索界面。

**不可抄点**：ZCode 是编辑器形态的产品，Moneyhelper 的入口是对话与 CLI。把编辑器交互
搬过来会破坏"记一句、问一句"的低摩擦定位。

## 三、dsh 深读

**核心主张**：没有内核，只有插件。模型、工具、技能、会话、沙箱、存储、循环、
调度、UI 全部是可替换组件，跑在 Cordis 插件框架上。

**架构可抄点**

1. **"一切皆插件"是拆分的终局标准**。不是"文件拆小"，而是"每块能独立替换"。
   判据：把 LLM 从 LiteLLM 换成别家，要改几个文件？把 SQLite 换成 Postgres，
   要改几个文件？Moneyhelper 现在前者 1 个（`llm.py`），后者需要动 `db/_core.py` 的连接层——
   已经接近可替换。
2. **事件源会话日志**。会话不是"当前状态"，而是"事件序列"，可回放到任意时点。
   Moneyhelper 的 `runs` 表存的是问答结果，不是事件流；provenance 存的是金额变动事件。
   如果按事件流重建，就能支持"回到上周三的账本状态看看"。
3. **能力缝三角**：模型能力 / 工具面 / 权限边界三者要匹配。模型弱就收窄工具面，
   权限大就要更强的模型判断。Moneyhelper 当前模型可换（LiteLLM），但工具面固定，
   权限边界只有大额阈值一条——三角不匹配。
4. **harness vs 框架的定位差异**。LangGraph 是"帮你搭流程的框架"，harness 是
   "直接能跑的完整执行环境"。Moneyhelper 介于两者之间：有 LangGraph 的图，也有自己的
   lifespan / 调度 / 存储。

**不可抄点**：dsh 面向编程任务，工具副作用集中在文件系统（可回滚）。财务场景的
副作用是真实账目与外部行情，可回滚性差得多，所以**审批必须比 dsh 更严**，
不能只依赖"插件声明的权限"。

|---|---|---|---|

| P0 | 收窄工具面：按路由结果只暴露相关工具 | pi 极简 4 工具 + dsh 能力缝三角 | `agent_config.get_agent_tools()` 已有白名单，改成按 route 动态收窄 |

## 五、与 Moneyhelper 现有设计的冲突点

1. **"一切皆插件" vs 单进程单体**。dsh 的插件化隐含多进程/热插拔，Moneyhelper 当前是
   单进程单库。插件化到极致会引入分布式复杂度，与"本地优先、双击即用"冲突。
   结论：**接口上插件化，部署上保持单体**——模块边界清晰，但运行时是一个进程。
2. **沙箱 vs 本地优先**。真沙箱（容器/VM）与"双击 EXE 就能用"冲突。
   结论：财务场景不需要执行沙箱，需要的是**写操作审批**——把沙箱的隔离意图
   用审批链实现。
3. **事件回放 vs 存储成本**。全量事件流会让库体积随使用时间线性增长。
   结论：只对**金额变动**做事件流（provenance 已经是），问答历史保持现状。

## 六、结论

四份 harness 的共同答案不是"更强的模型"，而是**用工程手段约束模型**：

- 工具面越窄，模型越不容易乱用（pi）
- 上下文越可控，长任务越不容易失焦（codex harness）
- 副作用越需审批，产品越可信（ZCode / dsh）

Moneyhelper 已经有三者的雏形：工具白名单、tiktoken 计数 + 摘要压缩、大额 HITL。
下一步的价值在于**把雏形补成完整机制**，而不是再引入一层框架。

具体执行顺序：P0 两项（审批全覆盖 + 工具面动态收窄）属于 M2，与协议补课
（MCP 全量暴露）天然同批；P1 的编排层收敛放在 M2.5（官方 saver 替换）一起做。
