**一句话结论**：现在是一个可运行、可审计、数字可复核，财税时序、可配置归因、调度告警、企业多主体合并、外部交接包、真实投递通道与 AI 托管规则都有真实数据源或真实出站动作的财务系统。用户既能手动走完整流程，也能把归因确认、税务交接、企业月结交给系统按预设规则执行；资料包能留档、能确认线下交接、能比对来源摘要，能通过用户自备 SMTP 真发信或签名 HTTPS 网关真 POST。它不是“全税种自动申报平台”，也不是法定合并报表系统；投递回执的 `accepted` 只代表对端受理，`duplicate` 只代表同一底稿幂等去重，都不是税局申报成功、银行付款成功或审计意见。外部动作仍受税局资质、持牌通道与接口准入约束，不能靠代码单方面宣称完成。

## 二、已交付功能清单

### 本轮归因托管（4.24.0）

- 新增第三个托管动作 `attribution_confirm`：按账期扫描规则候选，只确认 `custom_rule` / `rule` 来源，`history` 同类不自动确认。
- 默认最低置信度 `0.7`，默认本批合计上限 `10000` 元；单次最多 100 条，超限部分在计划里显示 `pending` / `skipped`，留给下一轮。
- 批量金额合计超过上限时，自动模式也回落 `awaiting`；缺候选时 `blocked` 并说明原因。
- 执行走 `batch_apply_confirmations` 单事务原子写；分类在计划后变化会整批拒绝。每条写确认快照，追加 `record_provenance` 证据，可在归因页回滚。
- `run-all` 顺序改为归因→企业月结→税务交接；前一步的分类确认先落地，后两步读到的是整理后的账。
- 前端托管台扩为三张动作卡，归因卡可配合计上限与最低置信度；切模式即保存，结果区分手动计划、候选笔数、已确认笔数、超限待确认与无候选阻断。
- 边界：只改流水分类，不动金额、日期与余额；不替用户判断历史同类；税局直连、银行划款、法定合并、社区发布仍未落地。截图 `209`–`212`。

### 上一轮 AI 托管台与电商经营测算（4.23.0）

- 新增 `autopilot_policies` / `autopilot_decisions` 两张表：策略按用户 + 动作保存模式、通道、金额阈值；每次评估/执行/阻断都落一条决策，最多保留 300 条/用户。
- 三档模式：`manual` 只出计划绝不执行；`assist` 出计划后等一次确认；`auto` 规则内直接执行；超阈值、缺通道、数据阻断回落为 `awaiting` 或 `blocked`。
- 两个真实动作：`tax_deliver` 复用税务核对包与 4.22 投递层，过滤 `filing_channel` 这类“本来就没有外部通道”的阻断项；`month_end_close` 复用 `enterprise_month_end` 工作流，幂等键按租户 + 账期。
- `run-all` 先月结、后税务交接；`dry_run` 只评估，不触发外部动作，仍记决策并标 `dry_run=true`。
- 决策值只有 `manual / awaiting / executed / blocked / failed`；重复投递返回 `duplicate`，不重复发信/重复 POST。
- 电商经营测算：纯确定性计算，覆盖 GMV、退款、订单、平台佣金、支付费率、推广、货品成本、履约、其他成本与税项；输出净利、净利率、单均净利、客单价、退款率、当前 ROAS、盈亏平衡广告费/ROAS 与告警。
- `ecommerce_scenarios` 存保存方案，可删除；测算不写账、不改账，只做经营口径对照。
- 连接中心新增「电商经营」分类（抖店、淘宝、拼多多、有赞），授权后只读订单/账单，不代运营、不代下单；插件市场新增 Playwright MCP（浏览器授权读取），不代下单、不改价。
- 前端新增 `autopilot` 与 `ecommerce` 顶层视图；托管台支持切模式即保存、按规则跑一次、只评估、确认执行与最近决策；电商页参数防抖自动算、保存/删除方案。
- 边界：税局直连仍需乐企/服务商，银行划款需持牌与授权，法定合并需审计口径，社区代发布需平台授权；内容社区本轮暂停，不新增假入口。截图 `199`–`208`。

### 上一轮外部投递通道（4.22.0）

- 两张新表：`external_channels` 存通道配置、启用状态、上次测试结果；`external_deliveries` 存投递幂等键、状态、收件人、请求摘要与回执。密钥只进 vault，列表不回显。
- 四类通道：`smtp`（税务/付款/合并）、`tax_gateway`（税务）、`bank_gateway`（付款）、`audit_gateway`（合并）。
- 真实动作：SMTP 用 `smtplib` 真发信，附包体 JSON、SHA256 摘要与付款 CSV；网关用 `httpx` 签名 POST，带时间戳、HMAC-SHA256 签名与幂等键。
- 安全默认：外部邮箱必须 STARTTLS/SSL；外部网关只允许 HTTPS；内网/保留地址默认拒绝；本机明文或 HTTP 联调需 `MH_ALLOW_LOCAL_CHANNELS=1`；无密钥、未启用、缺地址时 fail-closed。
- 投递规则：只把 2xx 视为受理；同一底稿重复点击返回 `duplicate`；成功自动进入交接台账，失败写 `HANDOFF_SEND_FAIL` 审计。
- 前端：四张通道卡、配置侧栏、二次确认投递、最近投递与台账投递徽章；中英文案补齐约 80 个键。
- 真实验收：本地 SMTP `127.0.0.1:2525` 真收测试邮件与业务邮件；本地 HTTP `127.0.0.1:9099/hook` 收到签名 POST 并返回 `SINK-RECEIPT-4220`；两类通道各完成一次真实投递，状态 `accepted` 并留痕。
- 边界：`accepted` 只代表对端受理，不代表税局申报成功、银行付款成功或审计意见；税局直连仍需乐企准入，资金划转仍需持牌通道，法定合并仍需审计口径，社区代发布仍需平台授权。截图 `192`–`198`。

### 上一轮交接留档与线下确认（4.21.0）

- 交接台账：`GET /api/external/handoffs`，合并 `HANDOFF` 与 `HANDOFF_ACK` 审计事件；返回总数、仅留档、已交接与边界说明。
- 留档：`POST /api/external/handoffs`，按类型与期间生成包并追加 `HANDOFF`；同 `packet_id` 幂等，重复调用 `created=false`。
- 线下确认：`POST /api/external/handoffs/ack`，只允许已留档的包转为 `handed_over`；未留档 404，重复确认 `updated=false`。
- 来源摘要：三类包统一带 32 位 `source_hash`，覆盖包体除生成时间与摘要本身外的全部字段；台账与当前同 `packet_id` 包比对并显示一致/不一致。
- 存储：不新增表、不写迁移；`detail` 存 JSON 并受审计函数 500 字符截断，备注限 120 字。
- 前端：三卡「留档」按钮、底部交接台账、操作备注、确认按钮、计数徽标与亮暗主题；截图 `181`–`183`。

### 企业侧

- 复式总账：科目表、期间、日记账、草稿→过账→冲销、试算平衡、期间锁。
- 报销申请与“申请人≠审批人”；采购到付款：供应商→采购单→应付→付款，逐步生成凭证。
- 银行对账：账户/金额/方向匹配、账实差额、签核门槛。
- 财报分析：三表输入、比率、杜邦、预警、报告文本；报表快照存取。
- 税务计算：增值税、企业所得税、个税、工资、综合税负、月结 12 项清单。
- 月末自动结账：先过账草稿再关账；已关账幂等；无期间静默跳过。
- 财税时序：按月聚合已过账凭证的收入、费用、利润、现金流入流出、税费计提/缴纳与凭证数；缺账月份返回 `missing`，不拿 0 冒充已结账。
- 多主体管理合并：集团范围、`full` 100% 全额纳入、`proportional` 按持股折算、人工抵销分录、合并三表与科目底稿；缺期间/无过账主体显式排除；不做 NCI、权益法、法定合并。

- 4.17.3 归因控制面：自定义规则融合候选、批量确认单事务、误判回滚仅在分类未被二次改动时生效，规则采纳/回滚统计与确认列表同源。

5. 收支归因：规则 + 历史候选、人工确认、确认留痕；无命中不编分类。
6. 代码合规扫描：本轮新增代码过 ruff；`check-duplicates.py` 仍剩 5 处存量助手重复（remote / shares / thread_context / longtask / personal_review），不能为过扫描改返回类型。
7. 调度重试与死信：幂等步骤指数退避、失败/部分失败写告警、确认与重放、启动补偿；原运行证据不被重放覆盖。
8. 告警前端：定时产出面板显示死信、未读数、确认与重放，演示环境完成真实重放。
9. 归因规则与批量操作：规则 CRUD/启用停用/测试预览，批量确认原子写，单笔撤销与回滚证据，采纳/回滚统计；演示重置同步清空归因表。
10. 企业多主体管理合并：集团与范围、100%/比例折算、抵销分录、集团三表、科目底稿、演示集团、前端财报页内视图与暗色适配；7 项定向测试与全量回归通过。

### P0：当前无阻断项

4.17.0 / 4.17.1 / 4.17.2 / 4.17.3 / 4.18.0 的 P0 已清空。停机补偿只覆盖可安全重放的月结；每小时同步与十分钟收件箱不补跑，避免重复导入，这是明确边界而不是遗漏。

### P1：平台能力补全

4.19.0 的三项 P1 已收口：资产调优候选、时序凭证下钻、归因商户/金额/成员维度。4.20.0 把税局申报、真实付款、法定合并前的可交接部分做成只读资料包；4.21.0 补上留档、线下确认与来源摘要核验；4.22.0 补上真实出站投递层（SMTP 真发信、签名 HTTPS 网关）；4.23.0 把税务交接与企业月结编排成可预设的托管规则，并补上电商经营测算与开放平台/MCP 入口；4.24.0 把月结前的归因确认纳入同一套托管契约。当前没有新的本地可交付 P1；再往前只能进入 P2 的外部资质项。

### P2：受外部资质约束，不能默认交付

1. 税局直连申报/缴款：需要“乐企”准入（营业收入、开票量、纳税信用等门槛）或服务商通道；当前没有资质，不能实现。4.22.0 已留签名 HTTPS 适配器，资质到位后填地址与密钥即可真实投递，但不生成申报结论。
2. 银行/券商真实资金划转：需要持牌通道与用户授权；默认只做 handoff，不自动划款。4.22.0 已留银行网关适配器，实际划款仍需持牌方回执。
3. 集团法定合并报表：需要审计口径、抵消分录与合并范围确认；当前只做管理分析。4.22.0 已留审计交接网关，不等于审计意见。
4. 五个内容社区“上线”：需要各平台账号、登录与发布授权；未获授权前只能准备素材，不能代发。

## 六、同步机制

1. 每次版本提交前：`git fetch` + `git ls-remote` 核对五远端 `main`，以远端 SHA 为准，不以推送命令的退出码为准。
2. 本文与 `CHANGELOG.md`、`docs/index.md`、`docs/index.zh.md`、版本文件同批更新。
3. 新增能力必须同时更新：已交付清单、待开发池、路线图、溯源表；四块缺一不算完成。
4. 文档里的每个“已交付”都必须能在仓库找到入口（路由/函数/测试），否则降级为“待开发”。
