# 回答依据与质量反馈

两项都嵌在原有聊天消息里，不新增侧栏、不新增顶层页面：回答下面多一行「依据」，操作条多一对赞/踩；汇总留在设置 → 质量与评测的原卡片里。

## 回答依据

每次成功回答在落库时同步写入 `runs.sources_json`，`GET /api/runs` 回放历史时带回 `sources`。

- **知识库来源**：按与回答相同的 BM25 口径检索已入库附件，同一附件多个片段只保留一条，最多 3 条。关闭知识库（`knowledge_enabled=off`）时不检索。
- **网页来源**：从回答正文抽取 `http(s)` 链接，去掉尾随中英文标点，过滤本机地址，同一域名只保留一条，最多 3 条。联网回答里模型写出的链接才会出现；没写链接就不补造。
- **顺序**：知识库在前，网页在后。知识库来源点击后打开对应附件预览；网页来源走现有「浏览器打开链接」事件。
- **边界**：这是「回答里实际出现的依据」，不是搜索引擎的完整引用链；摘要与正文仍以模型回答为准，点开原文才能核对。

`backend/app/qa_sources.py` 负责抽取与合并，`backend/app/routes/qa.py` 在保存回答前调用，SSE 的 `final` 事件同时下发 `sources` 和本轮 `run_id`。新回答无需刷新即可点赞/点踩。

## 质量反馈

`POST /api/runs/{run_id}/feedback`，body `{"rating": 1 | -1 | 0, "reason": "..."}`。

- `1` 为赞，`-1` 为踩，`0` 为撤销；其他值返回 400，run 不存在返回 404。
- 只能改当前租户自己的 run；反馈写入 `feedback_rating`、`feedback_reason`、`feedback_at`。
- 踩之后出现四个原因：不准确、答非所问、太啰嗦、数字不对；选一个即提交，也可以只踩不选。
- 前端先乐观更新消息状态，接口成功后以服务端返回值覆盖；失败回滚并提示。
- 历史消息加载后保留已提交的赞/踩与原因。

`GET /api/feedback/summary` 按当前租户聚合总数、赞、踩、满意率与最常见原因。设置 → 质量与评测的「模型评测」卡片顶部展示这一行，失败时静默，不影响评测本身。

## 数据与迁移

`runs` 新增四列：`sources_json`、`feedback_rating`、`feedback_reason`、`feedback_at`。新库由 `schema_personal.py` 建列，老库由 `migrate_columns.py` 补列；启动时自动迁移，不需要手工改表。

## 验证入口

- 真实模型回答后看正文下方「依据」与操作条赞/踩。
- 点踩选原因，再刷新会话，确认红踩与原因仍在。
- 设置 → 质量与评测 → 模型评测，确认「回答反馈」行计数变化。
