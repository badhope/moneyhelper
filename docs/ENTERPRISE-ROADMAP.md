# Moneyhelper 企业化改造方案

> 状态：2026-11-11 静态审查 + 第一批改造落地后的工作文档。
> 适用范围：`D:\Moneyhelper`（commit `bd213b2` 起）。
> 说明：本文件是工程方案，不是完整代码审计、安全认证或工期承诺。

## 1. 结论

### 1.1 项目现在是什么

当前产品更接近 **面向个人、家庭和小微经营者的 AI 财务助手**：

- 核心数据是持仓、流水、债务、目标、预算，而不是企业账套、科目、凭证、往来单位；
- 首页与新用户引导围绕“记账 / 加自选 / 配 AI”，不是“建企业 / 建账套 / 配岗位”；
- “部门”是 AI 工位与派工，不是企业组织架构、岗位职责与职责分离；
- 财报页分析外部传入的三表 JSON，不是从总账生成报表；
- 发票偏识别归档，月结清单状态存在浏览器 localStorage，工资偏计算器；
- 已有 FastAPI + React + SQLite、多用户与部分租户过滤、AI 工具策略、审批、审计、MCP 等可复用基础。

### 1.2 目标应该是什么

不建议把目标定义成“在聊天框旁边加满所有岗位按钮”。建议定义为：

> **以企业组织、业务单据和复式账务为事实来源，以流程、权限和审计为约束，以 AI 为辅助执行层，逐步覆盖企业主要岗位的协同平台。**

三层职责必须分开：

1. **业务/账务系统**：订单、合同、发票、凭证、付款、余额由确定性代码与数据库决定。
2. **流程/权限系统**：谁可发起、审核、过账、付款、撤回，由岗位、数据范围和职责分离决定。
3. **AI 层**：提取、解释、草稿、建议、异常提示；不得绕过规则直接制造正式账务或外部动作。

“全岗位”是长期愿景，不是一期交付范围。第一期应做一个真正闭环的财务场景，再向外扩展。

## 2. 现状与差距

| 维度 | 现状（证据） | 企业目标 | 差距 |
|---|---|---|---|
| 产品主模型 | `frontend/src/lib/types.ts` 以 `Position/Transaction/Debt/Goal/Dashboard` 为主 | 租户/法人/账套/科目/凭证/期间/往来 | 需要新建领域模型，不是加字段 |
| 导航 | `FinancePage.tsx` 分“日常/分析/账务/连接”，仍以个人理财为主 | 工作台/待办/单据/财务/组织 | 信息架构需按岗位重组 |

### 2.1 必须先修的安全/可信问题

已修复（本批，均有回归）：

- **MCP stdio 配置可导致任意命令执行**：`PUT /api/mcp/servers` 默认拒绝 `command`，只有显式设置 `MONEYHELPER_ALLOW_STDIO_MCP=1` 才允许；备份恢复同样默认丢弃 stdio 配置。
- **停用账号旧 JWT 仍可访问**：统一鉴权闸现在校验账号存在且未停用；`user_count` 改为统计全部账号，避免“全部停用 = 退回无账号模式”的绕过。
- **实例级管理缺边界**：MCP 配置、审计清空、备份恢复统一走 `require_instance_admin`；普通用户 403，单机无账号模式仍可用。
- **审计归属失真**：actor 改记稳定身份（`user:<id>` / 共享口令用户名 / local），401/403 都记为 AUTH，清空审计本身也会留下记录。
- **审计不可校验**：新增租户内 SHA-256 哈希链（`prev_hash`/`entry_hash`）与 `GET /api/audit/verify`；改字段、删中间行会断链；物理清空默认拒绝，仅 `MONEYHELPER_ALLOW_AUDIT_CLEAR=1` 可开。
- **外部 MCP 工具按名称猜只读**：改为只信服务器显式声明的 `ToolAnnotations.readOnlyHint`，未声明默认不进入模型工具面；Moneyhelper 自己的 MCP Server 已按本地策略标注只读/写。
- **JSON 备份覆盖不完整**：补入模拟盘账户/成交/快照、净值快照、家庭议案/投票、再平衡目标、定投计划、财报分析，并做“导出→恢复”往返测试。
- **账本更新允许无穷数**：更新与批量入账统一拒绝 0/NaN/±Inf。
- **税务接口把显式 0 当缺省值**：`_f()` 只对缺省/None/空串回落默认值，零税率不再被替换。

仍待处理（按优先级）：

1. **审计仍缺外部锚点**：哈希链可发现改字段/删中间行，但删除末尾记录、重算整条链仍无法自证；后续把链头定期写入独立存储/WORM 日志，并补保留/归档策略。
2. **MCP 配置仍是实例级共享**：管理员边界已加，但尚未做“实例配置 vs 租户配置”的分离。
3. **备份/恢复的运维级验证**：已补业务表往返，仍需大库、损坏包、跨版本、恢复耗时与回滚演练。
4. **外部连接器凭据与权限**：券商/银行连接的凭据管理、最小权限与操作审计仍需单独评估。

原则：在上述问题修复并有回归测试前，不公开部署，不接真实企业账务、银行付款或高权限生产系统。

## 3. 目标架构

```text
岗位工作台（财务/出纳/采购/销售/人事/管理层/管理员）
                    │
AI 助手与知识层（提取/草稿/解释/风险提示，不直接过账）
                    │
流程与权限层（申请→校验→审批→执行→对账→归档；RBAC + 数据范围）
                    │
企业业务域（总账/应收应付/报销/发票/合同/采购/薪资/资金）
                    │
企业基础能力（租户/法人/组织/岗位/权限/审计/文档/通知）
                    │
基础设施（数据库/文件/任务/密钥/监控/备份恢复）
```

### 3.1 设计原则

1. 一个企业可有多个法人与账套；`user_id` 不等于租户。
2. 每个财务数字可回溯到业务单据、附件、审批人与操作记录。
3. 借贷平衡、期间、税额、汇率由确定性代码执行；AI 只给建议。
4. 金额统一固定精度与舍入规则（本项目税额已统一 `Decimal + ROUND_HALF_UP`）。
5. 权限同时控制“操作”和“数据范围”。
6. 付款、删除、过账、关账、外部发送默认需要显式授权。
7. AI 输出区分事实、计算、推断、待确认。
8. 租户隔离在 API、SQL、后台任务、缓存、文件五个层面验证。

### 阶段 2.5：权限点字典与 Casbin 影子模式（切片 7a，已落地）

- **权限点字典**（`backend/app/authz.py`）：17 个权限点，`<域>:<动作>` 形式，
  覆盖组织/总账/报销/付款/银行流水/对账 6 个域；角色 → 权限点是纯数据 + 纯函数，
  未知角色与未知权限点一律 fail-closed；
- **Casbin 影子引擎**（`backend/app/authz_engine.py`）：RBAC with domains，
  domain = tenant_id；在真实请求上跑同一套策略，**只记录不拦截**；
  casbin 缺失 / 模型解析失败 / 写库失败一律降级，业务路径完全不受影响；
- **影子决策表** `authz_shadow_log`：并排记录「字典判定」与「代码实际是否放行」，
  `mismatch=1` 即两者不一致——这是切到 Casbin 拦截之前必须先修掉的清单；
- **接入点**：5 个业务域的权限闸（组织/总账/报销/付款/对账）统一经过
  `backend/app/authz_guard.py`，漏记一处就等于该权限点没覆盖；
- **实现改用字典派生角色（7a-2）**：各域不再手写角色白名单，
  改由 `authz.roles_with(permission_id)` 从字典派生。
  这修掉了影子模式发现的第一条真实差异：**`viewer`（只读角色）原本也能新建报销单**
  （代码按"任意成员"放行），现在按字典拒绝。
  回归测试 `test_derived_role_sets_match_previous_hardcoded_lists` 锁死"派生结果 == 原白名单"，
  防止以后调字典时无声地改变某个域的准入角色；
- **API**：`GET /api/authz/permissions`、`GET /api/authz/shadow`、
  `GET /api/authz/shadow/summary`、`DELETE /api/authz/shadow`、`GET /api/authz/status`；
  读接口走 `require_instance_admin`；
- **开关**：`MONEYHELPER_AUTHZ_SHADOW=0` 可整体停用影子（业务照常）；
- **边界**：Casbin 引擎本身**仍然只记录、不拦截**；真正的拦截留给后续切片，
  前提是影子 mismatch 长期为 0。

验收：字典与实现一致时 mismatch 恒为 0；人为破坏 Casbin 判定时业务请求结果不变。

### 阶段 3：财务闭环 MVP

**已落地（切片 4，总账内核）：**

- `gl_accounts / gl_periods / gl_entries / gl_entry_lines` 四张租户表；
- 金额用整数分；科目编码唯一、期间开/关、草稿凭证、过账、反冲、试算表；
- 借贷不平衡、期间关闭、重复反冲、跨租户引用均有回归测试；
- 备份/恢复已包含总账，内部 ID 重新映射；
- 总账前端已接入（科目/期间/凭证/试算表），桌面与移动端有截图检查；
- 报销闭环已接入（切片 5b）：草稿→提交→审核（申请人≠审批人）→凭证草稿；审批通过不自动过账；
- 付款与银行匹配已接入（切片 6a）：付款登记、流水手工/CSV 导入、按账户+金额+方向匹配/取消、未匹配汇总；
- 对账签核已接入（切片 6b）：对账单余额 vs 账面余额、差额/未匹配双门禁、签核人留痕；
- **尚未接线**：差额自动生成调整凭证、发票验真；现有单式 `transactions` 不自动生成凭证；
- **账本归属策略已定稿（切片 7c）**：见
  [LEDGER-TENANT-STRATEGY.md](LEDGER-TENANT-STRATEGY.md)——
  当前**不做双写、不做账本迁移**，而是显式划界：
  个人理财域永远属于登录用户，企业财务域永远属于当前工作租户；
  迁移到 `tenant_id` 的前置条件（法人/账套模型、复合主键去键、家庭共享语义）尚未满足。

选一个场景做穿：**报销/发票 → 审核 → 凭证 → 付款记录 → 银行对账**。

最小能力：

1. 报销单与附件；AI 提取并标注置信度。
2. 规则校验：金额、重复单、费用归属、预算。
3. 审批：申请人≠审批人；金额触发多级。
4. 生成**待审核凭证草稿**；会计确认后过账。
5. 期间控制、借贷平衡、反冲。
6. 出纳付款；银行流水导入与匹配；未匹配队列。
7. 全链路追溯与审计。

验收：试算平衡；期间锁有效；重复提交不重复入账；每个数字可回溯。

### 阶段 4：岗位扩展

按客户价值排序：采购/应付 → 销售/应收 → 合同 → 人事薪资 → 资金/预算 → 管理层报表。每扩一个域，先定义单据、状态机、权限和审计，再接 AI。

### 阶段 5：企业交付

SSO/MFA、密钥管理、审计留存、备份/PITR、监控告警、性能与故障演练、渗透测试、合规评估。根据真实规模决定 PostgreSQL/多实例，不提前堆分布式组件。

## 5. 技术选型结论（build vs buy）

| 层 | 结论 | 理由 |
|---|---|---|
| 复式总账 | **自研薄内核** | 难点是租户、期间、审批、中国税制与导入链路，通用 ERP 不适配嵌入式产品 |
| 权限 | **PyCasbin** | Apache-2.0、成熟、domain 模型适配多租户；Oso 已归档，不用 |
| 审批 | **自研审批域 + python-statemachine** | 状态机只做原语；多级/会签/委派/审计仍是产品域 |
| ORM/迁移 | **SQLAlchemy 2.0 + Alembic 增量** | 不一次重写 300+ 处裸 SQL；新域先 ORM，旧域冻结 |
| 数据库 | SQLite（桌面）+ PostgreSQL（云多租户） | 双 dialect CI，逐步收敛方言差异 |
| XIRR | **pyxirr**（已替换） | Rust 实现，处理多根/不收敛，删约 100 行手写数值代码 |
| OCR | RapidOCR | 离线、Apache-2.0、体积可控 |
| 发票模板 | invoice2data | MIT，和现有二维码/OFD/正则互补 |
| 对账匹配 | RapidFuzz + 自建银行适配器 | 中国银行无统一开源标准；模糊匹配用成熟库 |
| beancount | **仅导出/测试 oracle** | GPL-2.0，文件型，不适合作为多租户运行时内核 |
| ERPNext/Odoo | **仅连接器** | 全栈 ERP，GPL/LGPL，运维重，领域错配 |
| SpiffWorkflow | 可选，客户要求 BPMN 时 | LGPL-3.0，Beta，需自建任务箱 |
| Temporal/Camunda | 暂不引入 | 审批 MVP 阶段运维成本过高，达阈值再评估 |

## 6. 界面调整

企业版首页建议：

- **我的工作台**：待办、待审批、异常、近期单据；
- **业务中心**：报销、发票、采购、销售、合同；
- **财务中心**：凭证、总账、应收应付、资金、对账、结账、报表；
- **AI 助手**：围绕当前单据与权限；
- **组织与管理**：员工、岗位、权限、审批、连接器、审计；
- **个人理财/投资**：独立入口，不与企业财务混用数据口径。

不同岗位不同工作台，但同一套后端权限控制，不能只靠隐藏菜单。
