# 4.25.0 银行流水批量匹配

> 口径时间：2026-11-25。版本 `4.25.0`（上一版 `4.24.0` 归因托管）。

## 一、为什么先做这个

4.24.0 把归因确认放进了托管台，月结前的“分类噪音”有了自动化出口。再往前一步，资金侧还有一件重复劳动：银行流水已经导进来了，付款也记过了，但两边没有配对。手工在银行页逐笔点“匹配”，既慢，又容易把同金额的两笔付款配错。

这轮不新增外部通道，也不碰发票与平台账单，只把已有的 `bank_transactions`、`payments`、`bank_match` 与撤销链路收成第四个托管动作：`bank_match`。目标是“只配唯一候选，歧义就跳过”，而不是追求匹配率。

## 二、动作契约

- 动作键：`bank_match`；默认 `manual`，沿用 `manual / assist / auto` 三档。
- 范围：只扫当前账期（`YYYY-MM`）内 `status=unmatched`、`direction=out` 的银行流水。
- 付款必须 `status=paid`；流水与付款必须同租户、同银行账户、同金额，且日期相差不超过窗口。
- 默认日期窗口 `3` 天，可配 `0–30` 天；默认本批合计上限 `50000` 元，`0` 表示不限。
- 单次最多 100 条；超过 100 条的部分返回 `pending`，不静默丢弃。
- 同一流水命中多笔付款、或同一付款命中多条流水时，整组判为歧义，跳过，不猜；没有唯一候选时动作 `blocked` 并说明原因。
- 本批合计金额超过上限时，`auto` 也回落 `awaiting`，必须再确认一次。
- 执行走 `bank_match_batch`：单事务原子写，任何一笔流水在计划后失效、付款状态变化、金额/账户不一致或日期超出窗口，整批回滚。
- 每条匹配写 `record_provenance("bank_match", ...)`，记录付款号、金额、流水日期、批次与账期；可在银行页撤销。
- `run-all` 顺序改为：银行流水匹配 → 归因确认 → 企业月结 → 税务交接。资金侧先配对，再做分类与月结。

## 三、数据与演示

- 新增 `backend/app/db/banking_bank_match.py`：`bank_match_candidates` 只读候选查询，`bank_match_batch` 原子批量写；导出到 `banking_bank.py`、`banking.py` 与 `db/__init__.py`。
- 单笔 `bank_match` 保留，批量动作不复用它的逐笔事务，避免“配到一半失败”。
- 演示重置现在清理 `bank_transactions` 与 `payments`，随后在企业总账初始化后种两组银行数据：
  - `云仓耗材 ¥148`，付款 `PAY-DEMO-4250-1`，流水 `DEMO-BANK-4250-1`，日期 `2026-11-18`；
  - `顺丰月结 ¥220`，付款 `PAY-DEMO-4250-2`，流水 `DEMO-BANK-4250-2`，日期 `2026-11-20`。
- 预期：匹配 2 笔、合计 ¥368；银行科目按 `gl_accounts.code='1001'` 查询，不硬编码账户 id。

## 四、前端

- 托管台从三张动作卡扩到四张：银行匹配、归因、税务、月结；桌面端 2×2，移动端单列。
- 银行卡可配“本批合计上限”与“日期窗口”，默认 `50000` / `3` 天；切模式即保存，失焦或保存时带上 `max_amount` 与 `window_days`。
- 结果区区分：手动只出计划、无候选阻断、超阈值待确认、执行成功、候选笔数、已配对笔数、本批金额与日期窗口。
- 中英文案同步；页面边界补上“流水匹配”；自助入口增加“银行流水与对账”。

## 六、本轮不做

- 发票批量入账仍缺可靠的发票→总账科目映射，不拿发票状态流转冒充入账。
- 平台账单对账仍缺文件收件箱、平台导出列映射与商户授权，不拿上传预览冒充自动对账。
- 不接银行直连、不代划款；流水来自用户导入，匹配只改流水与付款的关系，不动金额与余额。
- 税局申报、法定合并、社区代发布仍受资质/授权约束，不进入本轮“已完成”。
