# AI 财政处理平台：赛道边界、竞品矩阵与可行性论证（4.17.0，4.17.1 能力补充）

> 调研时间：2026-11-24。方法：只用公开可核验的产品页、官方文档与监管规范；没有把营销话术当成能力事实。
> 结论先行：**可以做“个人全周期陪跑 + 企业财政职能托管（不含税局申报/资金划转）”，不能宣称“全税种自动申报 + 无人化替代财政所有岗位”。**

## 一、两条赛道的真实边界

### 1. 通用 AI 理财工具

主流产品的能力集中在“记录、预算、报表、提醒、内容社区”。随手记公开页强调多维度记账、账户/资产负债、18 种报表、家庭多人协作；鲨鱼记账强调 3 秒记账、消费趋势与预算预警，高级能力走会员；Firefly III 是自托管复式记账，明确“无 AI、无云”，强在预算、规则、导入、报表和 REST API。它们共同的短板是：

- 资产端与负债端多为“记账口径”，不是会计口径；转账、成本、收益容易混。
- “AI 建议”常是内容推荐或话术，不是可复核的计算结果。
- 自动化局限在提醒/重复记账，不处理结账、对账、税负与期间锁。
- 个人与家庭、个人与小微公司之间没有同一套总账，数据需要二次搬运。

参考：[随手记官方下载页](http://www.feidee.com/money/download/download-center.jsp?item=ios)、[鲨鱼记账应用页](https://m.wandoujia.com/mip/apps/7630424/)、[Firefly III 官方](https://www.firefly-iii.org/)、[Firefly III 文档](https://docs.firefly-iii.org/)。

### 2. 开源财税自动化/ERP

ERPNext 公开宣称 100% 开源、支持多主体多币种、总账、应收应付、财务报表、中国增值税与金税集成；Odoo 会计强调 AI 发票数字化、银行同步（官方称 28,000+ 银行）、智能对账（官方称 95% 自动匹配）、多公司合并与本地化税包；Beancount 是纯文本复式记账，强在“每笔分录必须平衡”、余额断言与脚本化报表。它们共同的短板是：

- 部署与实施重，个人用户几乎不可能开箱即用。
- 中国企业落地依赖本地化包、服务商与税局通道，开源代码本身不提供准入资质。
- 功能面很宽，但“AI 自主决策”通常停留在 OCR、建议与问答，不承担资金/申报责任。
- 个人理财与企业总账通常分成两套产品，跨场景体验断裂。

参考：[ERPNext 中国页](https://erpnext.com)、[ERPNext 记账](https://erpnext.com/accounting/open-source-bookkeeping)、[Odoo 会计](https://www.odoo.com/zh_CN/app/accounting)、[Odoo 功能](https://www.odoo.com/zh_CN/app/accounting-features)、[Beancount 文档](https://beancount.github.io/docs/)。

### 3. 中国税务自动化的硬门槛

“全税种智能申报”不是产品功能，是资质与通道问题。上海税务局《乐企自用的规范指引（2025 版）》明确：直连单位及备案使用单位上一年度营业收入合计 **5000 万元以上**，申请前 12 个月累计开票量及受票量合计 **不低于 1 万份**或累计开票金额 **不低于 1 亿元**，上一年度纳税信用 **A 级或 B 级**，近 3 年无重大税收违法，并具备信息化、安全、运维能力。金财互联、金蝶等厂商的“一键申报”背后是自建/合作的税局通道与多年合规积累，不是一段开源代码。

参考：[国家税务总局上海市税务局·乐企自用规范指引（2025版）](https://shanghai.chinatax.gov.cn/tax/xxgk/tzgg/202304/t466805.html)、[金财互联智能算税申报](https://www.jchl.com/chanpinfuwu/productSssb/index.html)、[金蝶 AI 星空税务云](https://m.kingdee.com/products/galaxy_taxation.html)。

**因此本产品的合规边界是：**

- 可以做：计税、税负测算、申报底稿、月结清单、报表、凭证、资金流分析、异常预警、申报材料导出。
- 不能默认做：替用户登录电子税务局、提交申报、缴款、代规划转资金。
- 如未来要做直连：必须先拿到乐企/服务商通道与企业授权，另立合规评审与安全评估，不能混在普通版本里静默上线。

### 矩阵读法

1. **我们不在“记账更快”上竞争**。3 秒记账是成熟红海，投入产出比低。
2. **我们不在“税局通道”上硬碰**。没有资质就没有申报权，硬做只会把用户置于合规风险。
3. **真正的空位是“个人资产 + 企业总账 + 可审计自动化”三件事同一条链路**。个人看到的是净资产、现金流、风险；企业看到的是凭证、期间、税负、报表；两边共用一套确定性内核与审计台账。
4. **AI 的差异化不是“会聊天”，是“只负责措辞、不碰数字”**。这正好补上通用理财工具“建议不可复核”和企业软件“操作太重”的两头空缺。

## 三、场景化边界：谁用、用到哪、不做什么

### 个人用户

**用**：一句话记账、资产负债全景、预算与现金流、持仓与集中度、订阅与异常、月度复盘、长期任务（投研/计划）。

**不用**：代下单、代划款、承诺收益、把模型预测当事实。

**交互原则**：默认全自动跑；在“资产调整、风险超阈值、月结异常”三个节点要求用户确认，其余只出报告。

### 企业用户

**用**：凭证录入与过账、期间关账、银行对账、报销/采购/应付/付款、财报分析、税负测算、月结清单、申报底稿导出、资金流看板。

**不用**：替企业向税局提交申报/缴款、替企业做法定审计意见、替企业做集团法定合并（除非另立项目）。

**交互原则**：AI 可以自动做“有明确规则、可回滚、可审计”的动作；涉及申报、付款、关账锁定，必须留下人工确认或双人复核记录。

## 四、可行性路径

### 已具备

- 确定性计算内核：金额、比率、税负、报表都由纯函数计算。
- 复式总账与期间锁：草稿→过账→冲销→关账，已有测试。
- 自动化底座：APScheduler + 月结/同步/收件箱真实任务；4.17.0 增加运行台账、串行锁、幂等键。
- 多租户/部门/成员：数据隔离已有；集团合并还停留在管理口径。
- 溯源：工具调用与回答可追溯；运行台账记录每一步返回值；4.17.1 归因候选带规则 id、命中词、置信度，确认后记录 before/after。
- 财税时序：4.17.1 只读已过账凭证，按月给出收入/费用/利润/现金/税费与缺账状态，不把缺账当 0。

### 待补齐（按优先级）

1. **调度韧性**：当前 APScheduler 是内存 JobStore，进程重启后靠代码重新注册；缺少“错过任务补偿”、重试退避、死信与告警。这是 7×24 的真空档，排在 4.17.2。
2. **归因规则可配置与批量确认**：4.17.1 已做“候选 + 单笔确认 + 留痕”，但规则阈值、同商户记忆、批量确认与撤回还没做。
3. **财税时序下钻**：月度汇总已通，凭证/发票级下钻与申报底稿联动仍缺。
4. **集团合并**：需要合并范围、抵消分录、内部交易标识；当前没有法定合并能力。
5. **压力测试基线**：4.17.0 已出确定性计算与 SQLite 并发报告；外部接口、网络故障、税局退回仍不在覆盖范围。

### 明确不可行（当前资质下）

- 直连税局申报/缴款：无乐企准入或服务商通道。
- 银行/券商真实资金划转：无持牌通道与用户强授权。
- 五个内容社区代发布：无账号登录与发布授权。
- “100% 场景覆盖”承诺：场景无穷，测试只能给出覆盖清单与失败样本，不能给绝对保证。

## 五、差异化建设路径

**一句话**：把“AI 原生”落在“可审计的自动化”上，而不是落在“AI 会写一段理财建议”上。

1. **同一内核，双场景**：个人净资产、企业总账、税负、现金流共用计算函数；不为两个产品各写一套。
2. **自动化有账本**：每次定时/手动执行都有 run id、步骤、耗时、返回值、错误；失败可见、可补跑、可幂等。
3. **人只在决策点出现**：资产调优、超阈值风险、申报/付款/关账确认；其余无人化。
4. **合规前置**：税局直连、资金划转、社区发布都先做“资质/授权检查”，不满足就只做导出与 handoff。
5. **开源只复用底层**：调度、图表、解析、模型路由用成熟库；财税规则、总账、审计链路自研并测试，不把核心账务交给不可控第三方。

## 六、本轮落地结论

| 论证项 | 结论 |
| --- | --- |
| 与普通理财 APP 的边界 | 普通 APP 停在“记录+建议”；本产品继续做“总账+结账+税负+审计” |
| 与开源财税系统的边界 | ERPNext/Odoo 强在广度和本地化实施；本产品强在个人/企业同栈、本地优先、AI 可审计 |
| 个人全场景追踪 | 已有资产、流水、持仓、订阅、现金流、健康评分；4.17.1 补上归因确认与财税时序，下一步是规则配置与批量确认 |
| 企业全链路看板 | 已有总账、采购、应付、对账、财报、税负；4.17.1 补上统一财税时间轴，集团法定合并仍未做 |
| 全自动闭环 | 可在“规则明确、可回滚”的范围落地；归因、申报、付款、关账锁定必须保留人工确认 |
| 极限压测 | 先做可复现的确定性计算与并发读写压测；不把“通过压测”写成“100% 场景覆盖” |

> 这份文档的作用不是给宣传页提供形容词，而是给开发排期划出“能做/不能做/先补什么”的硬线。任何后续版本偏离这条线，都应在评审里被挡住。
